# Measuring Grounding in a LoRA-Fine-Tuned Language Model

An evaluation suite that distinguishes a model which learned a task from one
that learned the *shape* of a task — built, tested, and applied to a model it
fine-tunes.

---

## The problem

Suppose you fine-tune a small model to interpret poems, and it returns this:

> *The poem reflects on the passage of time and the way memory shapes
> experience. It uses natural imagery to suggest change, and contrasts light
> and darkness to mark shifts in feeling. The tone is reflective and somewhat
> melancholy.*

That reads like a competent interpretation. It is also true of an enormous
number of poems, and would fit most of this corpus unchanged. The model may
not have engaged with the particular poem in front of it at all — it may have
learned what interpretations *sound like*.

**This failure is not invisible.** Put that text beside the actual poem and a
careful reader would often notice it says nothing specific. That is worth
stating plainly, because the difficulty is not detection:

- there are **750 outputs** to check — 150 poems × 5 model variants — each
  needing to be read against its source poem
- "too generic" is a judgement call with no obvious cut-off, and two people
  will draw the line differently
- **it produces no number**, so two models cannot be compared, and there is no
  way to say whether fine-tuning helped or hurt

The problem is not that this failure hides. It is that it is **unmeasured** —
and an unmeasured failure cannot be compared across models, tracked as things
change, reported, or defended.

**This project builds that measurement, then applies it to a model it
fine-tunes.**

## Why it is worth the effort

Fine-tuning on synthetic data — targets generated by a larger model — is now
the common way to adapt a small model, because expert-written targets are
expensive and generated ones are not.

Gudibande et al. (2023) studied models trained this way and found they "are
adept at mimicking ChatGPT's style but not its factuality": human raters
scored them well because style is the part that transfers most readily. That
was a different setting — larger models, a different task, human raters rather
than a mechanical check — so it does not predict what happens here. It does
make the question worth asking rather than assuming, which is the reason this
project measures instead of eyeballing.

The poetry task is the testbed, not the application.

## The core idea: the swap test

Take an interpretation `I` that a model produced for poem `P`. Show a judge the
same interpretation three times, against three different poems:

| Condition | Poem shown | Asks |
|---|---|---|
| `matched` | `P` itself | — |
| `mismatched_random` | random poem, **different author** | does this text fit *any* poem? |
| `mismatched_same_author` | different poem, **same author** | does it fit any poem *by this poet*? |

Two numbers come out:

- **Grounding gap** = matched − mismatched_random
- **Poem-level gap** = matched − mismatched_same_author

A small gap means the interpretation is interpretation-shaped text that fits
anything. A large gap means it is anchored to the specific poem in front of it.

The third condition exists because an author's themes recur. A model that
learned *"Dickinson writes about death, immortality and nature"* can produce a
plausible interpretation of an unseen Dickinson poem **without reading it** —
and that text still beats a random Whitman poem. Only comparing against another
Dickinson poem closes that escape route. The difference between the two gaps is
the share of apparent grounding that is really just recognising the poet.

**Why this works without ground truth.** There is no reference "correct
interpretation" to compare against, and no expert on hand to write one. The
swap test avoids needing one by being *relative*: a judge that scores
generously, or harshly, or inconsistently does so in both conditions, and the
bias cancels in the difference.

## Experimental design

Five arms. Each pairwise contrast isolates exactly one mechanism.

| Arm | Mechanism | What it is |
|---|---|---|
| `template` | none | one fixed generic interpretation, emitted for every poem |
| `base_zero` | none | base model, zero-shot |
| `base_few` | in-context | base model, 3 examples in the prompt |
| `lora_r8` | weight update | LoRA, rank 8 |
| `lora_r16` | weight update | LoRA, rank 16 |

| Contrast | Question |
|---|---|
| `template` vs `base_few` | does the model beat a trivial generic baseline at all? |
| `base_zero` vs `base_few` | what do in-context examples contribute? |
| `base_few` vs `lora_r8` | what do weight updates add over prompting? — **the headline** |
| `lora_r8` vs `lora_r16` | what does adapter capacity contribute? |

`template` is the trivial baseline: fixed text that never sees the poem. It may
score surprisingly well. That would be a legitimate and interesting result, not
a bug — it is precisely the number that says how much of a "good" score is
available for free.

## What is measured

**Model-free first**, because these cost nothing and cannot be argued with:

- format compliance — does the output follow the required four-part schema?
- grounding rate — do quoted lines actually appear in the poem? (substring match)
- length distribution — proving arms do not differ merely in verbosity

**Then judge-based**, with two judges from different model families:

- pairwise win rate against `base_few`, with binomial confidence intervals
- position-bias flip rate — every comparison run twice with the order swapped
- the swap test — grounding gap and poem-level gap per arm
- inter-judge agreement (Cohen's κ), so the instrument itself is measured

Hypotheses are **pre-registered** before any results exist, with the statistical
test for each fixed in advance. Nulls are reported as plainly as positives, and
a null means "no detected difference" — never "proof of equality."

## What this project does not claim

Stated up front, because a limitation found by a reader is worth less than one
you named yourself.

- **No claim about interpretation quality.** Only about textual grounding.
  There is no expert reference, so "is this a *good* reading of the poem" is
  outside what any measurement here can support.
- **The training targets are synthetic.** The student's ceiling is the
  teacher's quality — so the teacher's hallucination rate is measured and
  reported, not assumed.
- **The base model was pretrained on this corpus.** Public-domain poetry is
  public domain because it is old and widely reproduced, which is exactly what
  puts it in web-scale pretraining data. A contamination probe measures how
  much of the corpus the base model can reproduce verbatim, and results are
  stratified by it — but this is measured, not solved.
- **Two judges, neither validated against human annotation** on this task.
  Agreement between two LLMs is weaker evidence than agreement with a person.
- **One task, one backbone, one teacher.** Nothing here generalises beyond this
  setup.

## Method notes

- **~2000 poems** from [PoetryDB](https://poetrydb.org), 8–100 lines,
  public domain.
- **5-fold grouped cross-validation, grouped by author.** Poems by one author
  are not independent samples, so an author never appears in both a training
  partition and its own evaluation set — the same principle as keeping one
  patient's scans out of both sides in medical ML (cf. `GroupKFold`).
- **Decoding is fixed identically across all arms.** Otherwise the comparison
  measures sampling settings rather than adaptation method.
- **Loss is masked to interpretation tokens only.** Prompt and target are
  tokenised separately and concatenated as id lists — never as one string,
  because BPE merges across the seam.

| Role | Model |
|---|---|
| Student | Qwen2.5-0.5B (base, not Instruct) |
| Teacher | DeepSeek (API) |
| Judge (primary) | GPT-4o-mini |
| Judge (secondary) | Gemini 2.5 Flash |

Four different model families. An evaluator recognises and favours its own
generations (Panickssery et al. 2024), so a judge sharing lineage with the
teacher or the student would inflate scores for reasons unrelated to grounding.

## Repository

```
config.py              all hyperparameters, model names, paths, seeds
src/
  data/                fetch, generate, filter, split
  model/               model loading, LoRA setup
  train/               training loop, sweep driver
  generate/            inference for all five arms
  eval/                format checks, grounding, judges, swap test,
                       contamination probe, metrics, prior-work comparison
  plots/               all figures
tests/                 tests where a silent bug would invalidate results
notebooks/             01_data, 02_training, 03_evaluation, 04_report
results/               runs.csv, adapters, figures
```

Logic lives in `src/` as tested functions. Notebooks import, call, and display
— they contain no implementation.

### Running it

Every module runs end-to-end on CPU in under a minute with tiny settings, so
bugs surface locally instead of after a GPU session spins up:

```bash
SMOKE=1 python -m src.train.loop
```

Print the resolved configuration for any run:

```bash
python config.py
```

Training and generation run on Kaggle (P100/T4). Everything else — the data
pipeline, both judges, all evaluation, every figure — runs locally on CPU.
